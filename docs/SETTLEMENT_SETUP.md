# Полная выплата по строке

Миграция 08 добавляет settled_at, settlement_source_id, settled_amount в существующую ledger_entries. Новых таблиц учёта нет. Начисления, веса, Make и интерфейс пока не меняются. При установке ни одна операция не помечается выплаченной.

Make вызывает public.settle_sheet_operation только после фактической выплаты и положительного статуса: Y «выданы деньги» для «доля от проекта», Z «обналичены бонусы» для бонусных типов. Включать в выборку ранее переданные начисления тоже: выплата происходит позже начисления. Пустые и отрицательные статусы не вызывают функцию и не отменяют старую выплату.

Параметры: p_operation_id=R, p_designer_id=A, p_operation_type=G, p_order_number=D, p_event_id=I, p_expected_amount=L для RUB или Q для LR. Сумма сверяется с SQL точно, не пересчитывается по текущим правилам. Перед запуском сверить Make с реальными типами полей и текущими формулами Google. При расхождении сумм исправляется причина, а не отключается контроль.

Функция находит исходную запись по проверенным текущим ключам TEST|PROJECT|project_id|type, TEST|ACTIVITY|activity_id, TEST|REFERRAL|invited_designer_id. Дизайнер проверяется с сохранением регистра TG-*; только Ddigits приводятся к верхнему регистру. Для реферала проверяется именно project_id исходного начисления, поэтому другой заказ приглашённого не подходит.

ID операции R должен оставаться постоянным. На одну запись начисления допускается одна выплата, на один R — одно начисление. Повтор с тем же R и той же суммой возвращает already_settled=true. Попытка использовать другой R для уже выплаченной записи или прежний R для другой записи отклоняется. Сумма исходного начисления после выплаты защищена CHECK от изменения. Частичных выплат нет. Возврат/исправление уже записанной выплаты — отдельная согласуемая процедура.

Приветственный бонус не поддерживается этой функцией, пока не определена его строка-источник в базе начислений. Прямые ручные записи без известных ключей также отклоняются.

settled_at — время фиксации в SQL, не дата банковского перевода. settled_amount хранится в исходной валюте: RUB для вознаграждения, LR для бонусов. Фактический рублёвый перевод при обмене LR и его курс здесь не фиксируются и не выводятся из предположений о курсе. Это не автоматическая платёжная система и не бухгалтерский документ.

После SQL необходим отдельный сценарий/ветка Make и изменение API кабинета на leroy_private.get_settlement_balance: accrued/paid/remaining в RUB и accrued/redeemed/remaining в LR. Квартальные окна, сгорание, заявки на выплату и действительный денежный перевод не включены.

Тест sql/tests/full_settlement.test.mjs использует @electric-sql/pglite и изолированную минимальную схему. Пройдены 28 проверок и повторная миграция. Реальный Supabase и параллельные внешние вызовы в тесте не использовались; блокировка ledger row и unique index обеспечивают базовую защиту конкуренции.
